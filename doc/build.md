# Build

How the engine is checked and tested, the demos are built for the browser and the app is built natively: the toolchain, the commands of `build.sh` and the build stamp they pass.

## The host toolchain

Odin at `~/opt/odin` (the dev-2026-09 nightly). The environment variable `ODIN` overrides the path to the compiler. Browser builds link with `wasm-ld`, which the link step calls from `PATH`. When `wasm-ld` is missing, `build.sh` wraps the Rust toolchain's `rust-lld` (`-flavor wasm`) in `tmp/linker-shims/wasm-ld` and puts that directory first on `PATH`, so lld or rustup is the one extra requirement. The native smoke run needs `xvfb-run`. glslang (the Homebrew formula `glslang`, its `glslangValidator` command) is optional: without it `./build.sh check` skips the shader validation with a note.

## build.sh

| Command | Runs |
| --- | --- |
| `./build.sh check` (the default) | `odin check src/engine -no-entry-point -vet -strict-style` with the build stamp define (the engine is a library package without `main`), the same check of the engine again for `-target:js_wasm32` so it compiles for both targets (test files carry `#+build !js`, since `core:testing` does not compile for the browser), then `odin check src/app -collection:shared=shared -vet -strict-style` with the build stamp define, then `odin check` of every `src/demos/*/` for `-target:js_wasm32`, then every shader under `src/engine/shaders/` is validated with `glslangValidator`, as it is and once more as a temporary copy whose first line is `#version 330 core`, the desktop profile the native build swaps in |
| `./build.sh test` | `odin test src/engine -all-packages -vet -strict-style` with the build stamp define, so the tests of the packages under `src/engine/` run too, then `odin test src/app -vet -strict-style` with the collection, the linker shims and the build stamp define |
| `./build.sh web <demo>` | builds `src/demos/<demo>` for the browser, see [The web build](#the-web-build) |
| `./build.sh debug` | builds `src/app` to `build/bedrock-array` with `-debug`, see [The native build](#the-native-build) |
| `./build.sh release` | the same build with `-o:speed` |
| `./build.sh smoke` | the debug build, then four runs of it under `xvfb-run`, three frames each of the menu, the models demo, the LOD demo and the smelter's pipeline editor, each failing on a printed `glGetError() returned` line |

Any other argument prints the usage to stderr and exits with status 2.

## The build stamp

The engine and the native commands pass `-define:BUILD_INFO="<commit> <UTC time>"`, for example `a1b2c3d+dirty 2026-10-18T12:00Z`, read by `build_stamp` in `src/engine/build_stamp.odin` and by `BUILD_INFO` in `src/app/main.odin`. The demo commands do not pass it yet: no demo shows the stamp, and Odin warns on an unused define. The commit and the time share one define so an all digit commit is never read as a number. The commit is `git rev-parse --short HEAD`, with `+dirty` appended when `git status --porcelain` prints anything, and `unknown` outside a repository. `BEDROCK_ARRAY_COMMIT` in the environment overrides it: an archive build has no `.git`, so the script building it passes the commit it was made from.

## The web build

`./build.sh web <demo>` runs `odin build src/demos/<demo> -target:js_wasm32 -vet -strict-style` and writes `build/web/<demo>/`: `index.html`, `demo.wasm`, `odin.js` (the toolchain's runtime from `core/sys/wasm/js/odin.js`), `style.css` and `labels.js`, a copy of `web/labels.js`, which starts the wasm in place of a bare `runWasm` call and moves the scene's label plaques each frame. `index.html` is `web/index.html` with every `__DEMO__` replaced by the demo's name, `style.css` a copy of `web/style.css`. Without a demo name, or with a name that has no `src/demos/<demo>/`, the command prints the usage and exits with status 2. `./build.sh check` checks every demo for the same target with the same flags.

`odin.js` fetches the wasm, so a page opened as `file://` does not run. To view a build locally: `python3 -m http.server --directory build/web/<demo> 8000`, then `http://localhost:8000/`.

## The native build

`./build.sh debug` and `./build.sh release` run `odin build src/app -out:build/bedrock-array -collection:shared=shared -vet -strict-style` with the build stamp define and `-debug` or `-o:speed`. raylib 6.0 comes from the `shared:raylib` collection, a copy of the toolchain's binding with an archive built from source ([shared/raylib/README.md](../shared/raylib/README.md) holds the why and the build record). The archive links X11, and Bazzite ships `libX11.so.6` and `libSDL3.so.0` without the unversioned development links the linker looks for, so the build creates `tmp/linker-shims/libX11.so` and `libSDL3.so` as symlinks to them and passes `-extra-linker-flags` pointing the linker at `tmp/linker-shims`.

The binary starts on a menu of the scene demos, the scenes and their data embedded by `src/app/demos.odin`, and shows the one entered first person with the mouse and the keys of the pages ([render.md](render.md), Scene files). The menu's rows scroll to keep the selected one above the glyph line. On the gamepad the d-pad or the left stick moves the menu's row, South enters the demo, East or Start leaves it back to the menu, East on the menu quits. In a demo North (Y) or the right shoulder cycles the scene's configuration forward and the left shoulder steps it back, named at the bottom right when the scene has more than one. On the keyboard the arrows move the row, Enter enters, Escape leaves the demo and on the menu quits, and C cycles the configuration, T toggles the tint of each model by its level of detail and F freezes every model's level. In a demo with levels of detail Back or Tab opens and closes a panel at the top left with the level dials (pixels per triangle, hysteresis, crossfade seconds, tint and freeze) and reads back the triangles drawn this frame and the count of models at each level: while it is open the d-pad and the arrows move its row and change the row's value instead of walking, rising, sinking or stepping the focus, and South or Enter resets the row to its default. In a scene that orbits its target the mouse turns only while its left button is down and the wheel zooms, each notch scaling the distance by exp(-0.1), and the left and right arrows, instead of walking, and the d-pad left and right step the focus to the previous or next model. It takes `--demo <name>`, one of `light`, `surface`, `cave`, `models`, `decimation`, `parts` and `lod` (the last only in the app, with no page), which starts in that demo instead of the menu, `--frames <n>`, which stops after n frames (0, the default, runs until the window closes or the menu is left), and `--windowed`, which keeps the 1280 by 720 window and the cursor instead of going borderless over the monitor with the cursor captured in a demo. `--view yaw,pitch,distance,x,y,z` (radians, metres, then the orbit's target) replaces the demo's start view, in both camera modes, and `--configuration <n>` starts in the scene's configuration n, taken modulo the scene's count. `--shot <path>` needs `--demo` or `--edit`: it draws `--frames` frames, at least 3, without the labels, the stamp, the configuration name and the LOD panel, writes the last frame to the path as a PNG, prints `shot: <path>` and exits with status 0, or with status 1 and a line on stderr when the image cannot be written. Any other argument, an unknown demo or a shot without a demo or an editor prints the usage and exits with status 2. When the window does not open or the scene does not load it exits with status 1 and a line on stderr. After the window opens it loads OpenGL 3.3 through GLFW's `glfwGetProcAddress`, so it links no libGL, and prints the GL vendor, renderer and version. After the first frame it reads `glGetError` once and on an error prints `gl error 0x...` on stderr and exits with status 1.

The menu's last row, `editor`, opens the smelter's pipeline editor ([pipeline_editor.md](workflows/pipeline_editor.md), The editor), and `--edit <machine>` starts in the editor of `data/machines/<machine>/pipeline.sjson`, the app run from the project root. Opening it runs the native steps, which takes a few seconds on the smelter. The steps stand as a line of machines, 2 m apart along x, walked with a fly camera at 2 m/s, the cursor captured as in a demo unless `--windowed`. The mouse turns the camera only from the editor's fourth frame, since raylib reports the cursor's first jump to the window's middle as a movement. The machine under the crosshair, else the nearest one, is selected, its plaque highlighted and its bounds drawn. The top left shows the machine (and `unsaved` after an edit), the colour mode (false colour, each part in a palette colour and triangles of no part grey, or the materials the machine's `brief.sjson` names) and a status line, with the step list under it, each row with its index, op, triangle count (or its state while it has no output) and key values. The build stamp sits at the top right.

The bar along the bottom names the mode (walk, brush, key panel, insert menu, or unsaved after a leave warned) and every action the mode takes, one plaque each, "keys / pad: action", scaled by the window's height like the menu and wrapping onto more rows. The bindings and the hints come from one table, `EDITOR_BINDINGS` in `src/app/editor_input.odin`. Every keyboard action has a pad binding, the left shoulder held as a modifier where the buttons run out (shown as `LB + A`). Every edit reruns the pipeline from the step it changed and marks the editor unsaved, and a step running an external tool shows as computing. The key panel changes a key by its step within its limits and resets it to the value a new step has. The insert menu inserts after the selected step with default keys. A step is never deleted from the import. Saving writes `pipeline.sjson` without the file's comments. While the panel, the insert menu or the brush is open the selection holds still. The brush works on an assign step whose select is strokes or selects no pieces (an inserted assign step): the crosshair is its cursor and a ring of its radius marks the hit, a paint adds a stroke there, an erase removes the stroke nearest the hit when the hit lies within its radius plus the brush's, the radius scales by 1.25 per notch between 2 and 50 mm, and the triangles each stroke takes show on the machine's plaque. A leave closes the insert menu, the panel or the brush first; with unsaved edits the first leave only warns and the second discards them. `--view` places the fly camera as in a demo, and a shot of the editor keeps the plaques, the step list and the hints, leaving out only the stamp, for example `xvfb-run -a -s "-screen 0 1280x720x24" env XDG_SESSION_TYPE=x11 build/bedrock-array --windowed --edit smelter --shot tmp/shots/editor.png --frames 3`. A pipeline file that is missing or malformed exits with status 1 and a line on stderr; a step that fails, such as an import whose source is missing, shows as failed with its message on its plaque and in the list.

The gamepad comes through SDL3's gamepad subsystem (`vendor:sdl3`, `src/app/gamepad.odin`), initialised after the window and never with SDL's video, which would compete with raylib's. The hint `SDL_JOYSTICK_HIDAPI_STEAM` is set first so a Steam Controller over Bluetooth is read by SDL's own driver (a Deck's built in pad is on by default), and `SDL_NO_SIGNAL_HANDLERS` so SDL leaves SIGINT and SIGTERM alone, since nothing reads the quit event it would make of them; for the same reason the poll flushes SDL's event queue each frame, which would otherwise fill up. At start the app prints `input: SDL sees <n> joysticks`, and when SDL fails to initialise it prints the reason on stderr and runs without a pad. Each frame it opens the first pad SDL lists when none is open and drops one that has gone, and reads SDL's standard mapping (the buttons named by position, South to North, plus Back, Start, the shoulders and the d-pad), so any pad SDL knows works the same. The left stick walks, the d-pad up and down rise and sink, the right stick turns at two radians a second, as on the pages, added to the keyboard and the mouse.

`./build.sh smoke` runs the debug build four times as `xvfb-run -a -s "-screen 0 1280x720x24" env XDG_SESSION_TYPE=x11 build/bedrock-array`, with `--frames 3` on the menu, then `--demo models --frames 3`, `--demo lod --frames 3` and `--edit smelter --frames 3`, so a link or window problem shows in a headless session and not on the couch. Each run fails on a printed `glGetError() returned` line: the debug build's GL binding drains every error right after the call that raised it and prints it, so the app's own one shot check only sees errors in the release build.

`tools/shoot.sh <demo> <out.png> [app arguments ...]` takes such a shot without a display: it runs `./build.sh debug` unless `build/bedrock-array` is newer than every file under `src/` and `data/`, creates the output's directory, and runs the app under the smoke run's `xvfb-run` with `--windowed --demo <demo> --shot <out.png>` and the rest, for example `tools/shoot.sh parts tmp/shots/parts.png --view 0.5,0.3,2.5,0,0.5,0 --configuration 2`. Xvfb renders with Mesa's llvmpipe, so a shot shows the renderer's output, not the driver's. `--scene-directory <dir>` takes the scene from `<dir>/scene.sjson` and its meshes from `<dir>/meshes/` at run time instead of an embedded demo, so a pipeline step is shot without becoming a demo first (the demo name `tools/shoot.sh` takes is then only a placeholder). `--camera-light` turns the scene's sun to come from above and beside the camera each frame, so a shot of any side is lit.

## Writing a demo

A demo is one package under `src/demos/<name>/`. `odin.js` runs its `main` once at load, then calls the exported `step :: proc(delta_time: f64) -> bool` every animation frame for as long as it returns true. Rendering goes through `vendor:wasm/WebGL` with WebGL2 calls only, never WebGL1 (CLAUDE.md, Stack). Input from `core:sys/wasm/js`: the `.Pointer_Down` event covers touch and mouse alike, so one listener serves the phone and the laptop. A scene demo is the engine's `Scene_Page` plus its scene file `data/demos/<name>/scene.sjson`, passed with `#load` to `scene_page_init` with the material library ([render.md](render.md), Scene files, holds the format), and the texture directory `data/materials/textures/` through `#load_directory`. The page brings the orbit input: drag, pinch and wheel.

## Installing the demos

`tools/install_web_build.sh [commit]` builds every demo of the commit (default `HEAD`) and installs the pages under `bin/web/`. It builds from a `git archive` of the commit in a temporary directory, so the working tree is never served and agents editing `src/` cannot break a page that is open. The archive has no `.git`, so the script passes the commit in `BEDROCK_ARRAY_COMMIT` for the build stamp. Each install goes to its own `bin/web/builds/<UTC time>-<commit>/` with an `index.html` at its root that links every demo and names the commit and the build time. One rename switches the `bin/web/current` link to it, so the server never finds the link missing, and the two newest builds stay (double buffering). Run it after every commit on `main`.

## The web host

`tools/bedrock-array-web.service` is a systemd user unit that serves `bin/web/current` with `python3 -m http.server` on port 8080, bound to every address. Enable it once, from the repository root: `ln -sfn "$PWD/tools/bedrock-array-web.service" ~/.config/systemd/user/`, then `systemctl --user daemon-reload`, then `systemctl --user enable --now bedrock-array-web.service`. The pages are at `http://192.168.1.7:8080/`, or `http://bazzite:8080/` where the name resolves. The firewalld zone (FedoraWorkstation) already opens TCP 1025 to 65535, so the port needs no firewall change. A user service runs while the user is logged in. `loginctl enable-linger` would keep it up without a login.

## Play build

`tools/install_play_build.sh [commit]` builds a commit (default HEAD) in release mode from a `git archive` into `bin/play/builds/<install time>-<commit>/`, switches `bin/play/current` to it in one rename, and writes the launcher `bin/bedrock-array`, which resolves the link at launch and passes its arguments to the binary. The archive has no `.git`, so the script passes the commit in `BEDROCK_ARRAY_COMMIT` for the build stamp. A build directory holds only the binary and `COMMIT`, since the binary embeds its scenes, meshes and textures with `#load`.

- The install never waits for the game: a running game keeps its build directory and the next launch takes the newest. The two newest builds stay; older ones go unless a game still runs from them.
- The installed game never reads the working tree, so edits to `src/` and `data/` cannot break a couch session.
- The launcher unsets `SDL_GAMECONTROLLER_IGNORE_DEVICES` and sets `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD=0`: in Game Mode Steam hands the game a virtual pad and tells SDL to ignore the real one.
- `BEDROCK_ARRAY_X11=1 bin/bedrock-array` makes GLFW take X11: the launcher unsets `WAYLAND_DISPLAY` and sets `XDG_SESSION_TYPE=x11`. Unsetting alone is not enough, since GLFW's Wayland connection falls back to the `wayland-0` socket. `BEDROCK_ARRAY_GAMESCOPE` holds gamescope's own arguments and runs the game inside gamescope: `BEDROCK_ARRAY_GAMESCOPE="-f -W 2880 -H 1920" bin/bedrock-array`. Without gamescope on the path it prints one line to stderr and runs the game directly.
- `--target user@host:path` (the Steam Deck) builds here exactly as a local install, copies the build directory and the launcher with `rsync` over `ssh`, switches the remote `current` link in one rename and removes older remote builds by the same rule. Nothing installs locally. The path after the colon takes the place of `bin/` (absolute, or relative to the remote home). `--help` prints the usage.

## Steam shortcut

- `tools/add_steam_shortcut.py` adds or updates the "Bedrock Array" non-Steam shortcut in `~/.steam/steam/userdata/<user>/config/shortcuts.vdf`, pointing at `bin/bedrock-array` beside its own `tools/` directory. `--user-id` picks the Steam user, `--dry-run` shows what would be written.
- It parses the binary VDF and refuses to write unless the existing file round trips through its parser byte for byte; other shortcuts stay untouched.
- Steam must be closed while it runs (`pgrep -x steam`), or Steam overwrites the file on exit.

## Large files

Binaries under the extensions `.gitattributes` lists (images, audio, models, fonts) are Git LFS objects on GitHub, text formats stay plain (DESIGN.md, Asset storage). `.gitattributes` is the one place the routing lives.

A fresh clone needs `git lfs install` once per machine (git-lfs from Homebrew here), then checkout fetches the objects.

Every fetch counts against the LFS bandwidth quota, so CI caches its LFS objects between runs and the Deck receives copies of the built tree, never a clone.
