## The way in: tech demos, then the engine, then the game

Tags: planning, process

The user's direction: start with a series of highly polished tech demos that settle water behaviour, the art direction and the like, and that define the asset workflows by producing each its first finished asset. Then focus on the engine before any game level design or world building. `PLAN.md` holds the series as a proposal, nine demos.

Later the same day the user set the delivery: small interactive web pages hosted on bazzite, explored on the phone and the laptop alike. So phase A's stack is Odin to wasm for the browser with WebGL2 rather than raylib, which waits for the native engine in phase B together with the Steam shortcut and the couch path, and the web host comes before the first demo so both devices judge every commit. The consequences for the renderer are in `DESIGN.md` (Renderer scope): WebGL2 is OpenGL ES 3.0 class, so stage 1's light clustering runs on the CPU into a light index texture and compute becomes an optional native upgrade. A side effect worth having: the Odin wasm toolchain is exercised from the first demo, before the modules of phase B need it. D6's audio needs a little Web Audio glue, and a secure context may be needed for some browser APIs on the phone (`SUGGESTIONS.md`).

Why demos without the wasm host: polish and workflow are what the demos are for, and the boundary would slow the iteration they exist for. The cost is contained by two rules in `CLAUDE.md`: kernels are pure procedures with tests from the first demo, and the renderer is driven by draw lists only, so phase B moves the code behind the natives rather than rewriting it.

The calls taken with the direction: a serial pipeline (one agent at a time, the implementer in the main checkout, no worktree per item, since the one minute cadence cannot afford a worktree set-up per step and nothing runs beside the one agent), the Mine oh Belowed engine side carried by copy and adaptation while the game side is rewritten as modules, the wasmtime and wasm bindings vendored as copies rather than submodules, module code compiling both to wasm and natively with the couch build always on wasm, AGPL-3.0 for everything for now with the licence question for a public modding API noted in `SUGGESTIONS.md`, and a public GitHub repository created by the main agent.

## 0002 landed: the browser build and the hello page

## 0008 landed: orbit input on the light demo

Tags: engine, render, web, input, cadence

The first input code, and the first finding against the toolchain's runtime: odin.js stores every i64 event field as a low word through DataView.setUint32 and a high word through floor(value / 2^32), so a fractional movement between -1 and 0 would arrive as -4294967296 (read in the code, not executed: no node on the machine). The drag therefore uses the client delta between events, which the pointer table holds anyway, and the rule for later input code is to read positions, never the movement fields, until the runtime is fixed or replaced. Two device side risks stay open for the user's check: a trackpad's many small wheel events each zoom by the full step, and a trackpad pinch arrives as ctrl+wheel that also zooms the page. Cadence: implementer 46 s of agent time (spawned 16:52, reported 16:53), reviewer 98 s, one fix by the main agent, the item committed at 16:57.

## 0028 designed: the material workflow

Tags: workflow, materials, design, cadence

The first asset workflow, the research lesson 3 of the definition asks for, run by a design agent with web search and read only probes of the machine. The facts that decided it: Blender 5.2 runs headless from its flatpak, Cycles on the CPU (HIP does not load on this GPU), a 1024 emission bake in 0.26 s, a 512 preview of a bevelled box in 1.8 s; the torus trick (the texture coordinate wrapped onto a torus feeding 4D noise) gave a seam difference of 0.0044 against 0.0049 between ordinary neighbours, so the maps tile without blending. Against it: generation in Odin as Mine oh Belowed did would rebuild every noise primitive and has no headless review render; Material Maker (MIT, 1.7 of 2026-07) exports from the command line but through Godot, which wants a display; local text to material models (StableMaterials, MatFuse) need ROCm, which does not support gfx1010 and whose community RDNA1 build was archived in February; hosted generators return an albedo with derived maps and drift between runs; CC0 scans carry the photographic grime the look excludes; noise in the fragment shader costs several octaves with derivatives per projection and scale. The VLMaterial paper (ICLR 2025, a model writing Blender node code and judging renders) describes what the chosen workflow does by hand, which is a reassurance that the shape is current.

Two choices made by the main agent on the report's open questions: the albedo map is near white and the preset tints it, so one set serves every family colour, as DESIGN.md's one palette per family wants; and the chipping is a shader rule against the edge distance, which lets a baked set serve any primitive and later any model with a curvature mask, at the price of the rule existing in GLSL and in the review sheet's nodes. The other two questions went to SUGGESTIONS.md. Cadence: the design agent 267 s (spawned 18:43, reported 18:48), about ninety thousand tokens, which is the research a workflow decision costs and not the step size the cadence rule is about.

## 0032 landed: texture sets reach the renderer

Tags: engine, render, cadence

Two facts the reviewer established by reading the decoder and the runtime rather than by running them: `png.destroy` frees the metadata and the image header through `context.allocator` whatever allocator loaded them, so a temp loaded image is destroyed under a swapped context, and the temp arena's free is a no-op, so the destroy does nothing and the arena holds the decoded images until something resets it.
