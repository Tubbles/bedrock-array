## The design session over the definition

Tags: architecture, design, planning, process

The user's `definition.md` was read and worked out section by section into `DESIGN.md`, each section proposed by the main agent and decided with the user in the same session: the engine and module split with its rule (work per voxel, pixel, sample or byte is engine, work per entity or rule is module), the natives and the rules for the crossing, the two API layers after Warcraft 3's natives and `Blizzard.j`, intercom through the engine with events and calls (which fixed the factory as one module, since a per entity per tick flow may not cross a border), cellular systems as engine kernels with block data rules, the look as stylised realism with consistency coming from the renderer and the material library, the underground as early game bootstrap and late game loot with machines on both levels, a surface start with powered pickaxes, Git LFS on GitHub now and self hosted later, and the Techtonica study with ILSpy and AssetRipper instead of Ghidra, since the game is a Mono build.

Grounding came from Heimdall's host source, Mine oh Belowed's cut brief 0146 and its audits, the raylib 6 bindings Mine oh Belowed vendors, and the Techtonica install on this machine. One claim went in unverified and was caught by the user: Mine oh Belowed's data directory was called a year's worth of work when its history spans ten days. The lesson is the global grounding rule applied to numbers in a design doc as strictly as to references in a PR.

## The way in: tech demos, then the engine, then the game

Tags: planning, process

The user's direction: start with a series of highly polished tech demos that settle water behaviour, the art direction and the like, and that define the asset workflows by producing each its first finished asset. Then focus on the engine before any game level design or world building. `PLAN.md` holds the series as a proposal, nine demos.

Later the same day the user set the delivery: small interactive web pages hosted on bazzite, explored on the phone and the laptop alike. So phase A's stack is Odin to wasm for the browser with WebGL2 rather than raylib, which waits for the native engine in phase B together with the Steam shortcut and the couch path, and the web host comes before the first demo so both devices judge every commit. The consequences for the renderer are in `DESIGN.md` (Renderer scope): WebGL2 is OpenGL ES 3.0 class, so stage 1's light clustering runs on the CPU into a light index texture and compute becomes an optional native upgrade. A side effect worth having: the Odin wasm toolchain is exercised from the first demo, before the modules of phase B need it. D6's audio needs a little Web Audio glue, and a secure context may be needed for some browser APIs on the phone (`SUGGESTIONS.md`).

Why demos without the wasm host: polish and workflow are what the demos are for, and the boundary would slow the iteration they exist for. The cost is contained by two rules in `CLAUDE.md`: kernels are pure procedures with tests from the first demo, and the renderer is driven by draw lists only, so phase B moves the code behind the natives rather than rewriting it.

The calls taken with the direction: a serial pipeline (one agent at a time, the implementer in the main checkout, no worktree per item, since the one minute cadence cannot afford a worktree set-up per step and nothing runs beside the one agent), the Mine oh Belowed engine side carried by copy and adaptation while the game side is rewritten as modules, the wasmtime and wasm bindings vendored as copies rather than submodules, module code compiling both to wasm and natively with the couch build always on wasm, AGPL-3.0 for everything for now with the licence question for a public modding API noted in `SUGGESTIONS.md`, and a public GitHub repository created by the main agent.

## The cadence

Tags: process

The user's one minute target per step is kept as a rule about what an agent has to read, not about how fast it thinks: the floor of a step is context loading, so the specification carries everything and the implementer never explores. The sizing numbers in `CLAUDE.md` (one to three files, about 150 lines, a ten line specification) are starting values. The one measured point for the shape: Mine oh Belowed landed 606 commits in ten days (2026-09-26 to 2026-10-05) with implement then review per commit, about sixty a day, though with up to four agents in parallel.

## 0001 landed: the build script and the build stamp

Tags: build, cadence

The first item through the serial pipeline. Cadence: the implementer took 33 s of agent time (51 s from spawn to report), the reviewer 55 s (101 s), both well under the one minute target for the agent and the cycle under three minutes with the main agent's work between. The reviewer reproduced two facts worth keeping: `odin check` on a package without `main` needs `-no-entry-point`, and a `-define` value made only of digits is typed as an integer, which is why the build stamp carries commit and time in one string. Test parameters stay `t` as in `core:testing` and Mine oh Belowed's 2019 uses, an idiom the full word rule does not override.

## 0002 landed: the browser build and the hello page

Tags: build, web, cadence

The first browser build met the one gap in the toolchain: Odin links `js_wasm32` output with `wasm-ld` from `PATH`, and bazzite has no lld. The choices were Homebrew's lld (which pulls the whole llvm formula), the Android SDK's LLD 9 from 2019, or the Rust toolchain's `rust-lld`, an LLD 22, found through `rustc --print sysroot`. The build script wraps the last in a shim under `tmp/`, after Mine oh Belowed's linker shim pattern, so nothing is installed and a machine with lld on the path never sees the shim. The review added that `odin check` never links, so the check command does not ask for a linker, and that a phone browser counts its URL bar into `100vh`, hence `100dvh` first. Cadence: implementer 86 s of agent time (154 s to report), one fix round of 30 s, reviewer 67 s (85 s); the cycle with the main agent's work came to six minutes, over the three minute target, with the linker gap as the cause.

## 0003 landed: the web host on bazzite

Tags: web, hosting, cadence

The demo pages are served by Python's `http.server` as a systemd user unit on port 8080, chosen over a real server because it is already on the machine, serves `.wasm` with the right type, follows the `current` link on every request, and the pages need nothing more than static files. The unit is enabled on bazzite (symlinked from `tools/`), the firewall zone already opened the port, and the first index is live at `http://192.168.1.7:8080/`. A finding of the day beside the item: the engine package does not compile for the browser target while its test files are in, because `core:testing` pulls `core:os`, which panics on js. Test files therefore carry `#+build !js`, written into item 0004 together with a second engine check for the browser target in `build.sh`. Cadence: implementer 65 s of agent time (87 s), reviewer 68 s (153 s, it ran the install three times), the cycle about four and a half minutes with the service enabled in between.

## 0006 landed: the material library

Tags: engine, materials, data, cadence

The first data file and the first strict parser. The reviewer probed the parser with a scratch test and found that Odin's SJSON parser accepts `NaN` and `Infinity` as floats, which the range checks let through, so the number reader rejects non finite values: a rule for every parser that follows. `core:encoding/json` compiles for the browser target without change, which 0007's demo depends on. Cadence: implementer 66 s of agent time (88 s), reviewer 61 s (83 s), one fix round of 26 s verified by the main agent instead of a second review, the cycle three and a half minutes.
