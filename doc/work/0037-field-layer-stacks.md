# 0037: The procedural fields as layer stacks

Status: verified (2026-10-18)

Goal: the user's ask (2026-10-18): the voronoi scales and noises of a material become a configurable list, one random process defined the same way everywhere, so the in game editor can later hook into it ("that's exactly the things I'd like to be able to adjust and tinker with in game later"). Every procedural field of a material (the mottle, the orange peel, the steel grain, the wear field) is a stack of layers in the parameter file, and the bake script evaluates stacks instead of holding one construction per field. The maps do not change: the refactor is verified by byte identical output. Refers to items 0030 and 0036.

## Specification (main agent, 2026-10-18)

- `data/materials/bake/painted_steel.sjson`: `seed` and `tile_metres` stay; a `fields` object holds one array of layers per field: `mottle = [ { kind = "noise" scale = 5 detail = 4 } ]`, `orange_peel = [ { kind = "noise" scale = 60 detail = 2 } ]`, `steel_grain = [ { kind = "noise" scale = 8 detail = 3 } ]`, `wear = [ { kind = "blobs" scale = 4 radius = 1.0 radius_variation = 0.7 }, { kind = "blobs" scale = 1.2 radius = 1.2 radius_variation = 0.7 combine = "max" }, { kind = "noise" scale = 1.1 detail = 1 combine = "gate" low = 0.4 high = 0.7 amount = 0.7 }, { kind = "noise" scale = 7 detail = 2 combine = "mix" amount = 0.35 } ]`, one layer per line, written SJSON style without commas; `paint = { mottle_amount = 0.08 roughness = 0.55 roughness_variation = 0.12 orange_peel_height = 0.0015 }` and `steel = { roughness = 0.35 roughness_variation = 0.1 }` keep only the assembly parameters (`mottle_scale`, `orange_peel_scale`, `steel.scale` and the old `wear_field` object go away).
- A layer: `kind` is `noise` (keys `scale`, `detail`; the 4D noise's Fac) or `blobs` (keys `scale`, `radius`, `radius_variation`; a 4D voronoi's F1 distance and the red of its cell colour as the per cell random, `radius_cell = radius * (1 - radius_variation + radius_variation * random)`, `clamp(1 - distance / radius_cell, 0, 1)`). `combine` says how the layer joins the stack's value so far, which starts at 0: `max` (the default), `add` (`value + amount * layer`, `amount` default 1), `multiply` (`value * layer`), `mix` (`mix(value, layer, amount)`), `gate` (`value * (1 - amount + amount * smoothstep(low, high, layer))`). Every layer reads the torus coordinate with the seed as today. An unknown key, kind or combine, or a missing key, raises an error naming the field and the layer index.
- `tools/materials/bake.py`: `field_stack(tree, coordinate, layers)` evaluates a stack with `layer_value` (one procedure per kind) and `combine_layer` (one small procedure per combine, dispatched by a dict); the channel table is built from `fields` by name; `wear_field_channel`, `flake_family`, `patch_factor` and the per field channel procedures go away. The assembly stays: albedo `1 - paint.mottle_amount * mottle`, height `paint.orange_peel_height * (orange_peel - 0.5)`, surface R `paint.roughness + paint.roughness_variation * (mottle - 0.5) * 2`, G `steel.roughness + steel.roughness_variation * (steel_grain - 0.5) * 2`, B `stretch(wear)`. The node graph must come out numerically the same as today's, so the maps do not change: the same operations in the same order (the first `max` layer against the zero start is the layer itself).
- `doc/workflows/materials.md`: a section "The fields" after The pipeline: a field is a stack of layers, the two kinds with their keys, the five combines with their formulas, the stack starting at 0, and the sentence that the stack is the contract an in game generator implements later (the live reroll call in SUGGESTIONS.md). The bake file bullet under Files points to it.
- `tools/materials/review.py` is untouched (it reads only `tile_metres` from the bake file).
